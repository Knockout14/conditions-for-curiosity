## What's live

Pushed to `main`, deployed to production: `conditionsforcuriosity.netlify.app/app/*`.
Noindexed and not linked from anywhere on the existing site — reachable by
direct URL only. Local git and the live production deploy are confirmed in
sync as of this writing (commit `57cb30c`).

**The full loop is built, onboarding through a completed night:**
episode-5 gate → name/email/age → three-variable comprehension check (each
answer coded correctly regardless of which option gets tapped, with its own
blurb) → weekly pick (drag to rank three candidates, one swap allowed
across the three, "edit your details" reachable from anywhere up to the
commitment screen) → "ready to be curious this week?" commitment → summary
→ **open (tonight's question) → the move (adult answers first, a
voice-to-text hint instead of building real audio capture) → reveal (recap
+ a category-based "why this works" note) → circle-back (did the child ask
a question back, optional note on what they said) → done.** Answering
circle-back is the one write that actually crosses a question off — see
below, that wasn't true for most of today.

Once all three of a week's questions are asked, the summary screen and a
new end-of-week screen both ask "when do you want to start next week,"
defaulting a calendar reminder to the coming Sunday at noon, with a
"pick again now" escape hatch for anyone who doesn't want to wait.

Two calendar buttons — Google Calendar (real prefill link) and Apple
Calendar (`.ics` download) — appear both for "remind me about tonight's
question" and "remind me to start next week." Both compute their target
fresh each time rather than hardcoding "first question," so they can't
drift out of sync with what's actually next.

## The bug this whole second half of the day was about

Until today, nothing ever wrote to `askedQuestionIds` or advanced
`weeklyPick.usedCount` — the exclusion logic in `weekly-candidates.mjs` was
correct from the start, but always ran against an empty list. A family
could see the same three questions again next week by pure chance. Fixed
by making circle-back the write: submitting it appends the question's id
permanently (not just for that week) and increments the count by one, not
by three. Confirmed directly — sampled the bank 5 times with an id already
marked asked; it never came back.

Two more gaps surfaced tracing that same question through to "can we tell
if a family is avoiding one":

- **Editing a pick and setting one fresh looked identical in the sheet.**
  `submit-pick.mjs` now carries `isEdit` — one `no` row is "set and forget,"
  a `no` followed by several `yes` rows is a family that kept adjusting.
- **Circle-back didn't record what position a question was asked from.**
  It now carries `rank`, snapshotted at the moment `open.html` picks up
  "what's next" — so a later reorder can't rewrite what an already-given
  answer's rank looked like.

And a "give me the actual answer, not scattered edits to reconstruct
myself" ask produced a third sheet tab, **Week Summary**: one row per
completed week, final pick order next to the order the three were actually
asked in. A mismatch there is the avoidance signal — cross-referenced
against Sheet1's edit trail, it's how you'd see a specific question getting
bumped or swapped instead of asked. Guarded against firing twice for the
same pick; fires from whichever screen a family lands on first after
finishing (`open.html` or `complete.html`).

**Bug found and fixed while wiring the above, not asked for:**
`complete.html`'s "all three asked" check compared against
`askedQuestionIds.size` — a count that only ever grows, across every week
a family ever completes. Left alone, it would have silently misfired
"done" starting week 2, before any of that week's actual three were asked.
Now checks that week's specific three ids.

## The three sheet tabs, at a glance

- **Sheet1** — one row per pick confirmation (fresh or edited, see `Edit?`).

- **Circle-back** — one row per question actually asked. Adult's answer,

- **Week Summary** — one row per completed week. Final order vs. actual ask

## The decision that shaped the data architecture: the bank is proprietary, and this repo is public

Mid-build, the call came down that the question bank — not each question
individually, but the curation and tagging across all 165 — counts as the
thing worth protecting, "at least [as much as] the organization of questions
and information." `conditions-for-curiosity` is a public GitHub repo, so
anything committed to it is exposed regardless of how the app uses it.

**The bank never touches this repo, in any form.** Not the markdown, not a
parsed JSON version, not even gitignored — gitignore only keeps git from
tracking a file, it does nothing to stop `netlify deploy` from uploading
whatever's sitting in the working directory. Proven the hard way: an early
draft deploy briefly served `app/data/questions.json` as a plain static
file despite it being gitignored. Both bad deploys were found and deleted
via `netlify api deleteDeploy` before this got documented anywhere public.
The actual fix was physical, not conventional — the source markdown and its
parsed JSON live outside the repo entirely, in the already-Nextcloud-synced
vault at `Claude Cowork HQ/Context/engineering-curiosity/product/`.

**Two Netlify Functions are the only way the app touches the bank**, both
reading from a private Netlify Blobs store (`question-bank`, key `all`)
that the public site can't serve directly:

- `weekly-candidates.mjs` — samples candidates (3 for a weekly pick, 1 for
  the "swap one" replacement) from the age-matched Raw/Found pool, one
  guaranteed Math + one guaranteed General-or-Both when sampling 3. Returns
  only `id`/`text`/`domain`/`bigIdea`/`category`.
- `questions-by-ids.mjs` — full fields (including the adult's answer seed)
  for a specific, already-confirmed set of ids. Hard-capped at 10 ids per
  call so it can't be walked into a bulk dump of the bank.

Updating the bank going forward: edit the markdown in the HQ vault, run
`node parse-bank.js` there, then from this repo —
`netlify blobs:set question-bank all --input "<HQ vault path>/questions.json"`.
Takes effect immediately, no redeploy.

## Submissions: Google Sheets, not Netlify-native

Three Functions write to three tabs of the same spreadsheet, all through a
shared `netlify/functions/_lib/google-sheets.mjs` — a hand-signed RS256 JWT
(`node:crypto`, no `googleapis` dependency) traded for an OAuth token,
straight to the Sheets API. Chosen over a second Blobs store specifically
because it comes with a viewer for free — no founder-facing digest page has
been built, and the spreadsheet itself is the digest for now.

Credentials are three Netlify env vars — `GOOGLE_SERVICE_ACCOUNT_EMAIL`,
`GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY`, `GOOGLE_SHEET_ID` — set via direct
HTTPS calls to Netlify's API, not the CLI (`netlify env:set` chokes on a
positional value starting with `-----BEGIN PRIVATE KEY-----`, parses it as
a flag). A backup copy of the service-account key JSON lives at
`Claude Cowork HQ/Projects/engineering-curiosity/app/google-sheets-service-account-key.json`
in the synced vault. If it's ever lost: Google Cloud Console → the
`sheets-writer` service account → Keys → delete the old one, create a new
one (same `client_email`, so re-sharing usually isn't even needed), reload
the env var. Done once already this session; costs about two minutes.

Quota headroom at expected volume (20–50 uses over the next week or two):
not a real constraint. Netlify Functions free tier is 125,000
invocations/month; Sheets API allows 300 writes/minute/project. Both are
2–3 orders of magnitude above anything this app will do at that scale.

**`d30101d`** — found while auditing a 20-item pre-launch checklist you'd
been given (custom 404, meta tags, robots.txt, sitemap, favicon set,
analytics, privacy policy, etc. — full results below): `submitPick`,
`submitCircleBack`, and `maybeSubmitWeekSummary` in `app.js` all caught
their own fetch failures and continued as if they'd succeeded. Concretely:
a bad connection during circle-back — the one write that actually crosses
a question off — could be silently lost while the app moved on to
`done.html` as though it saved. `postJSON` also had no timeout, so a
genuinely stalled (not failed, just silent) connection could leave a
"Saving…" button stuck indefinitely — the specific gap flagged after the
Sept 10/11 review but not fixed then. The read side had the same shape of
problem: `open.html`, `complete.html`, and `pick.html` all `await`ed their
initial question-bank fetch with no `try`/`catch`, so a failed load just
left a permanently blank screen, forever.

Fixed: `postJSON` now aborts after 15s (deliberately generous — a Netlify
Function cold start plus a Sheets write is typically under 2-3s, so this
is 5-10x headroom, not a tight ceiling meant to catch ordinary slow wifi);
write failures now show an inline error and a "Try again" instead of
racing ahead; read failures show a retry message instead of a blank
screen; `maybeSubmitWeekSummary` only marks itself sent once the write
actually succeeds, so a failure just retries on the next screen load
instead of that founder-digest row being gone for good.

**Decision made during a friction self-review** (prompted by you asking
directly whether any of this added unnecessary friction to something
you want people to actually use): the first version of the retry logic
locked in the submitted data at the first click, so editing an answer
after a failed save — more note text, a different card order — would've
been silently dropped on retry. Fixed before shipping: `pick.html` needed
no locking at all (`CFC.patch()` overwrites cleanly, so it just re-reads
the live card order on every attempt, including retries); `circleback.html`
genuinely needs one narrow lock (`markQuestionAsked()` isn't idempotent —
calling it twice would double-count a question as asked), so only that
one piece is captured once, with the note text and yes/no selection read
fresh on every attempt. None of this changes the successful path — same
taps, same timing either way.
